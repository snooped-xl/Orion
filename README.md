# Orion

A native Linux script workspace with a Flutter Material 3 interface and genuine **Monaco Editor 0.57.0** embedded through WebKitGTK. The compact shell uses dark charcoal surfaces, blue actions, the supplied transparent Orion wordmark in the titlebar, tabbed scripts and a collapsible console.

The default window is 822×523, matching the chosen desktop window, with a 720×480 minimum. Roboto Flex uses a shared, aligned text scale throughout the interface; JetBrains Mono remains the editor font. A quiet navigation rail, natural-width file and execution groups, two-column script cards and integrated settings reduce visual clutter. Execute is the strongest action. Selective flat corners connect controls and active tabs. Narrow layouts retain every action, using labelled icon controls with tooltips when space is limited. Navigation hover and keyboard focus stay inside the small icon indicator, with one flat corner; clicking changes it to blue without a full-tile ripple or focus overlay. Spring press feedback and directional fade-through page swaps preserve workspace state, with reduced motion respected throughout.

UI Selection checkmarks indicate interfaces ready to use without known bugs, rather than exact visual accuracy. Orion, Synapse X, Synapse OG, Xeno and AWP currently have this mark; other interfaces may be unfinished or unpolished.

**Settings** groups window, editor and workspace controls. Always on top, minimap, automatic suggestions, bracket colours and whitespace are saved independently for Orion. Font size, line numbers, word wrap and local recovery remain available. Editor changes apply without replacing scripts or undo history; Ctrl+Space still requests completion when automatic suggestions are off. On native GNOME Wayland, always on top uses the included compositor companion; X11 uses the window manager hint.

**Getting started** is a four-step introduction required on a fresh installation. It explains placing `Orion Bridge.lua` in your executor's autoexecute folder, provides real Save script, Copy script and Open folder actions, recommends the executor's auto attach setting, and introduces Executor Quick Launch as a coming-soon feature. Completion is saved only when you choose Open Orion. Settings → Replay intro opens the guide again without clearing completion, changing your page, or replacing scripts. Existing installations retain their completed state. The guide follows every main Orion theme, custom colours and logos, compact layouts and reduced motion.

Tutorial steps use a 540 ms directional fade-through: departing content clears first, followed by a staggered spring entrance and a sweeping progress indicator. Navigation stays anchored. Setup feedback and scroll position remain steady during exit; quick reversals replace the current transition, and reduced motion swaps instantly.

Normal main-Orion launches also have a separate 950 ms entrance: the wordmark arrives, leaves upward, and a themed cover slides up to reveal the current page. It runs once per launch, without replaying on navigation or returning from another interface. Source interfaces keep their own introductions; Theme Studio previews omit both sequences. Reduced motion reveals the workspace immediately. A read-only code preview stays underneath the cover while native Monaco is protected from input.

Autocomplete uses a simple tonal Material sheet with quiet type details and an inset selection. Glassy follows the active theme's surface, text and accent colours with a translucent popup. Icons and labels remain sharp; source interface completion styles stay separate.

Right-click an editor tab for Rename tab, Save, Save as, and Close tab. Actions address that tab without switching away from the active script. Rename keeps its source and editor state; existing-file tab names survive Save and workspace recovery. Closing still confirms unsaved edits. The small context menu follows all Orion themes.

**Local scripts** live in a dedicated `scripts` directory inside Orion's application data folder (`~/.local/share/dev.snooped.orion/scripts` on Linux). The editor's list browses these files and folders independently of its tabs. The main editor’s Save and Save As dialogs start in this directory. Use **Open scripts folder** to add `.lua`, `.luau` or `.txt` files; external changes refresh automatically. The list's plus creates a real script file, while the editor's tab plus creates a draft. `Special/Orion Bridge.lua` is included on first use, without overwriting an existing copy. Right-click a script → **Code** to choose None, White, Blue, Green, Red or Special; assignments are saved alongside the scripts. Special uses continuously moving white, blue, green and red text, with a static gradient when reduced motion is enabled.

**Window modes** live together in Settings → Window. Compact mode tightens the header, navigation, tabs, toolbars, script list and console, morphing the default window to 740×470. Custom normal windows shrink proportionally, respecting a 680×420 minimum. Enlarged mode uses a 1045×648 window with regular control sizes. The modes are mutually exclusive and saved for startup; switching a mode off restores normal bounds. Both use the existing 480 ms window morph, with immediate resizing for reduced motion. Editor font size, GUI scale, scripts and Monaco undo history remain independent. Other interfaces retain their own source dimensions.

On Linux, launch placement captures the monitor containing the pointer before loading settings, then centers the selected window profile on that monitor. Pointer coordinates choose the monitor, never the window position. X11 uses logical GDK monitor geometry; GNOME Wayland uses the included authenticated compositor companion. Reserved desktop panels constrain placement only when necessary to keep the window visible. Companion windows keep their independent positioning.

The Flutter motion curves use Google's public [Expressive spatial/effects spring tokens](https://github.com/androidx/androidx/blob/androidx-main/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/tokens/ExpressiveMotionTokens.kt), following the [motion physics guidance](https://m3.material.io/styles/motion/overview/how-it-works). Spatial movement can settle with a small overshoot; fades stay bounded. Material supports [individual corner customization](https://developer.android.com/reference/com/google/android/material/shape/ShapeAppearanceModel.Builder).

## Run

Verified with Flutter 3.47.7 / Dart 3.13.5. Linux build dependencies are Clang, CMake, Ninja, pkg-config, GTK 3 and WebKitGTK 4.1 development headers, plus libstdc++ development files.

On Debian/Ubuntu, the WebKit development package is `libwebkit2gtk-4.1-dev`; the compiled app requires the `libwebkit2gtk-4.1-0` runtime. Other distributions need their equivalent WebKitGTK 4.1 packages. Check the build dependency with `pkg-config --modversion webkit2gtk-4.1`.

```bash
flutter pub get
flutter run -d linux
```

For a release build:

```bash
./scripts/build-linux.sh
./build/linux/x64/release/bundle/orion
```

The optional `--showcase` recording mode retains the earlier three-second showcase on an already configured profile.

For a desktop launcher with the supplied small Orion logo, run `./scripts/install-desktop.sh` after building. The portable Linux package includes `./install-desktop.sh` for the same user-local setup. Re-run it after relocating the bundle.

Keep the full `bundle` directory together when distributing the app, including `data/monaco`. A compiled Linux x64 bundle is also supplied separately. Its launcher requires no Flutter SDK. The two desktop window plugins are bundled as local source dependencies, with their Linux fixes and upstream licenses in `packages/`. The local compatibility fixes preserve shared graphics contexts and remove per-window event hooks when companions close, so closing a child leaves the main editor running.


## Theme Control

Theme Control is its own destination in Orion's rail. Settings now contains editor preferences and shortcuts. Easy theme applies an accent, two to four gradient stops and angle, surface tint, and outline strength across the Material UI and native Monaco. Fine tuning provides individual color-role overrides, including the editor. Preset base palettes stay separate from those manual overrides, so Easy tint and gradients also work when starting from Original Orion. The existing charcoal/blue Orion Expressive palette is restored with Reset to default. Original Orion uses the original source's #181A1B → #08090A graphite backdrop and thin outlines, with silver actions, neutral selections and grayscale Material controls. Original uses a single continuous window gradient: the editor, header, panels, tabs and resting controls are transparent, with thin outlines and restrained hover/selection layers. The Linux WebKit editor clears its own surface and uses the same window-coordinate backdrop as Flutter, so the background stays continuous instead of restarting inside the editor. This also avoids retained-pixel trails in WebKitGTK software rendering. Floating menus remain readable, and explicit Fine tuning surface overrides can restore an individual fill. Its monochrome palette also carries through editor hover, search and selection chrome; syntax highlighting stays readable. Previously selected built-in Original themes update automatically while custom colors remain intact. Additional gradient starters are included.

Material Rain is the third default theme: black surfaces without gradients, deep blue actions, dense small glass rain and 90% window opacity (10% desktop transparency). Its Flutter/Dart simulation adapts Lucas Bebber's [Codrops RainEffect](https://github.com/codrops/RainEffect): small, quick sliding drops coalesce, clear condensation and leave fine beads and short wet trails. Narrow wet highlights keep the drops visible on black while gentle refraction keeps text readable. A GPU compositor refracts the live UI through each water lens and trail, including Flutter menus and native Monaco. Dry pixels stay transparent to preserve smooth direct UI rendering; the rain layer never takes pointer or keyboard input. The source and MIT notice are bundled in `assets/effects/`.

Rain and window opacity can be adjusted independently under Layout & motion and are included in saved themes and JSON import/export. Reduced motion freezes the droplet simulation while the refracted UI still updates. Minimized windows stop simulation and texture captures; window morphs preserve proportional droplet positions. Switching to another interface restores normal opacity and disables the effect.

**Glassy** is the fourth default theme. A light neutral tint and blue actions sit on one continuous glass window, with no default background gradient. The default tint is 63% opaque, leaving 37% of the processed desktop visible while foreground text stays opaque. A rounded bevel and a gentle convex body bend the background, with a small amount of optical softening. On GNOME, Orion's optional compositor companion refracts the actual wallpaper and live windows behind Orion. The transparency slider changes the background tint while text and controls remain opaque. Navigation, script lists and controls inherit that material without repeated rims. Motion respects Reduce motion; Light mode uses an icy silver palette. Easy theme, advanced edits, saved looks and JSON import/export preserve the effect. Reset to default restores Orion Expressive.

**Blue Glass** is a fifth primary preset, preserving the chosen blue/slate gradient, angle, tint, 63% window opacity and Glassy optics. It can be selected and customized like the other presets. Orion Expressive remains the default for fresh installations and Reset to default.

Controls on an existing glass sheet use thin tinted overlays rather than another glass lens, following Apple's [Liquid Glass layering guidance](https://developer.apple.com/videos/play/wwdc2025/219/). The resting navigation stays quiet and its selected/hovered capsule belongs to the sidebar material.

Install the GNOME companion with `scripts/install-gnome-glass.sh --enable` in the source project, or `./install-gnome-glass.sh --enable` in the portable release. A first installation may require logging out and back in. It affects only windows authorized by their own Orion process, restores normal rendering when Glass is disabled, and leaves other extensions and desktop settings alone. Unsupported desktops keep the internal Flutter glass fallback. The companion adapts the MIT [Liquid Glass for GNOME Shell](https://github.com/ryohsuke1231/liquid-glass), pinned to `05d7697eb94ce1ddf2207431d196d71e99dd5b4c`. Background pixels stay in the compositor; no desktop image is exported to Orion or written to disk. See [integration and license](linux/gnome/orion-glass@orion.local/ORION_VENDOR.md).

The internal Flutter refraction shader comes from MIT [Liquid Glass Easy](https://github.com/AhmeedGamil/liquid_glass_easy), pinned to v5.0.0 at `8e253fee087ba1d3c0928bea4c877427a36e4889`. Its Skia path bends a shared owned backdrop along a narrow curved edge band, keeping centers free of blanket blur, zoom and white illumination. It remains available for previews, opaque Glass, and desktops without the companion. See [vendored integration](packages/liquid_glass_easy/ORION_VENDOR.md). This recreates the treatment; it is not Apple's native renderer.

For transparent compositor Glass, Monaco keeps its native editing, focus, undo and autocomplete while Flutter displays its clean alpha snapshots. This avoids Linux WebKit's stale transparent display pixels without fading the code. Other themes retain direct native rendering and their existing backing surfaces. Rounded frames composite once before antialiasing, and the original wordmark uses mipmapped downsampling at small sizes.

Save named themes locally, apply or delete them, and share theme settings with validated JSON import/export. Dark, light and system modes, the UI scale slider, compact mode and Reduce motion live under Layout & motion. Client management, editor menus, command palette, script previews, color pickers and logo cropping follow the active Theme Control palette, including custom gradients and surface overrides. Themes preserve documents, undo history, source-interface preferences and layout settings. Theme Control affects Orion; the recreated interfaces keep their own themes.

The Logo section accepts PNG, JPEG or WebP and opens a Flutter crop editor with a fixed 1408×387 transparent canvas matching the normal wordmark. Images initially fit fully inside that frame; drag, zoom, Fit whole image and Fill frame control placement. Apply stores the resulting PNG locally, while Cancel leaves the current logo intact. Restore Orion logo works independently of color resets. Imported image files can be moved or deleted afterward. Branding is cached and excluded from recurring companion-window state traffic; Orion’s Studio receives it once when opening its preview.

Material color roles and component theming follow the [Material 3 color system](https://m3.material.io/styles/color/the-color-system) and [Flutter theme guidance](https://docs.flutter.dev/cookbook/design/themes).

Orion, Synapse V3, Blue, X and OG share **Theme Studio**. It replaces the four Synapse theme panels and Live Edit; Orion keeps its existing Theme Control with an additional **Theme Studio** button for advanced editing. Open it from the interface’s theme/settings controls, or press **Ctrl+Alt+Shift+T** while one of these five interfaces is active. It opens an independent, resizable Material 3 window with the real interface on a selectable canvas, searchable layers, an inspector, undo/redo, and JSON import/export. A named Saved themes library supports saving, loading, renaming, deleting and exporting complete themes, including embedded images. Loading a saved theme changes the draft; Apply commits it to the interface. Changes remain in the Studio until **Apply**; closing with changes offers Apply, Discard or Keep editing. Unapplied drafts survive an owner-driven close or interface switch.

Theme Studio uses a joined tonal workbench, consistent property sections and visible Edit, Theme, Images and Saved tabs. The 20-pixel native window curve also follows its input region and resize handles; maximized/fullscreen edges are square. Compact windows open Layers in a drawer. Canvas elements have working move/resize handles; zoomed previews pan by dragging empty canvas or using the middle mouse button. Fit recenters the preview. Saving a loaded look creates a copy; Update selected replaces it explicitly. Its connected control groups follow [Google’s Material button-group guidance](https://github.com/material-components/material-components-android/blob/master/docs/components/ButtonGroup.md).

Orion’s canvas previews Editor, Scripts, UI Selection, Theme Control and Settings. Its gradients, Material Rain, dark/light mode and existing easy themes remain available; the normal color and logo controls continue to work after advanced edits.

Canvas windows use their own viewport and the current GUI scale. Orion includes its actual rounded frame, border and desktop controls; preview controls do not affect the Studio window. Move/resize handles and inspector sizes stay in source coordinates at every zoom and GUI scale. Runtime client output is excluded from the isolated design snapshot. Synapse editor fallbacks and Studio previews use Luau syntax colours from the native Monaco palettes, including comments, strings, keywords and numbers.

Easy theme recolours the whole interface from background, accent and text colours; Original, Midnight, Ocean and Ember presets are included. The inspector edits individual colours, element offsets, dimensions, corners, opacity and UI typeface. Images can be used as backgrounds, overlays, logos or element fills, with fit and opacity controls. PNG, JPEG and WebP data are embedded in the saved theme. Each settings, script-hub, console and undocked-editor target has its own colours and layers. Actual separate windows have editable default dimensions; embedded pages share the main window size. Applying a size updates open windows, and Original size restores the source dimensions. Monaco also follows applied editor colours, images, opacity and corners. The retired Synapse Error Logging controls and editor diagnostic markers are disabled; real Orion Bridge client output, warnings and errors remain visible.

## Orion Bridge

The original Orion v2 bridge is ported to Dart and starts once in the primary Linux process on `127.0.0.1:31337`. All ten interfaces and their native companion windows share it. Open **Clients** in the editor, copy the loader/full script or save `Orion Bridge.lua`, and run it in your existing client environment. The manager shows Roblox display names, assigned UserN identifiers, transports and pending queues. Execute sends the current source to all connected clients or an explicit selection. An empty selection never broadcasts. Disconnect clears that session and its queue; a running bridge script can reconnect automatically, so this does not close the game.

The three original transports (`port_bridge`, `stream_bridge`, `compat_bridge`), v2 query/header handshake, identifier collision handling, heartbeat/expiry, two-second long polling, eight-item batches, UTF-8/base64 source, per-client queues, execution results and mirrored client console output are preserved. All original script aliases and `/status` work. Existing request-capable and GET-only bridge scripts remain compatible. The bundled Lua script preserves generation cleanup, transport fallback, player names, console forwarding, error results and teleport reloading, with improved JSON escaping and failed-handshake handling.

Bridge replacement uses a bounded generation tag on the handshake and subsequent requests, so an old polling instance cannot consume new work or post late logs/results. Numeric handshakes cannot roll back to an older generation. Legacy clients without tags remain compatible in untagged sessions. Pending startup is settled during shutdown, allowing a clean immediate restart. The Lua client retains logs/results through temporary outages with bounded retry queues and decoded acknowledgment checks; both client execution IDs and server result acknowledgments are deduplicated within bounded history. Startup waits up to five seconds for a display name and refreshes it in later handshakes.

Run `python3 tool/bridge_client_smoke.py` for 20 deterministic tests of the actual bundled Lua asset, using the system Lua 5.4 library and mocked Roblox/HTTP APIs. It does not start a game, make network requests, or read an application profile. These checks cover display-name readiness/privacy, cancellation, retries, duplicate IDs, queue bounds, GET fallback, generation tags and broken optional executor helpers.

A Material 3 Expressive notification uses **Orion Bridge** as its title, **Executor Connected! (&lt;detected name&gt;)** as its subject, and the Roblox player’s display name underneath. It appears for about four seconds at the top right of the monitor hosting Orion. The Lua bridge obtains the name through `identifyexecutor()` before its first handshake, independently of the HTTP transport. Executor version reporting stays in the in-game console and is never added to the notification. Legacy or unknown executors use the same title with the generic **Executor Connected!** subject. The new Lua bridge reads `LocalPlayer.DisplayName` and waits briefly for the local player at startup; if that property is unavailable, it shows Unknown instead of falling back to the account name. The compatible `username` field now carries the display name, with `display_name` taking precedence on newer servers. Notification surfaces follow Theme Control's Easy gradients (including their angle and stops), palette, light/dark mode, surface tint, fine color overrides and outline strength. Original Orion uses its own graphite gradient and thin neutral border. Explicit elevated-surface overrides take priority over gradients; theme changes apply to subsequent queued notifications. It does not take keyboard focus, pauses while hovered and supports dismissal/reduced motion. Each new client gets its own queued announcement. Linux uses GTK's actual owner monitor; GNOME Wayland uses an isolated XWayland notification surface because Wayland does not provide absolute placement for ordinary app windows. A standard desktop notification is the fallback when that surface is unavailable.

Connections are runtime state and never restored as live after restart. Companion windows send ordered target/execution commands to the primary engine, keeping a single listener. Local-only request validation and bounded clients, queues, bodies, scripts and logs prevent runaway memory growth; scripts larger than 2 MiB report an editor error. This is a bridge to an existing client execution environment; the Flutter desktop does not itself run Luau or inject into another process.

The hub uses the four providers identified in the [original Orion ScriptHubService](https://github.com/snooped-xl/Orion/blob/main/ScriptHubService.cs), with a native Dart implementation adapted to their current response formats. Listings and source code come from the providers; demonstration results are not substituted on failure.

## Performance

Native editor changes are acknowledged locally instead of serializing every document back to Monaco on each keystroke or cursor move. Real file replacements, model changes and editor preferences still synchronize in full, with native edits protected from stale replies. Luau completion and hover share model-version analysis; editing and Undo invalidate that cache. Theme listeners rebuild only when their selected appearance changes, and cursor updates repaint the status independently of the workspace.

Tab rebuilds share one immutable document snapshot, avoiding a separate whole-list copy for each tab. Collapsed consoles skip unused history filtering, and Settings and UI Selection ignore unrelated document updates while still following their own controls and inherited themes. These changes preserve the existing layout, effects and animation timing.

Glassy keeps full-resolution native editor captures. Its live mirror negotiates lossless raw RGBA instead of compressing and decompressing PNG every frame; unchanged native frame IDs reuse the existing Flutter image without transferring the pixels again. Frozen previews and fallback hosts retain lossless PNG and their worker/cache path. Capture accelerates during interaction, retains the original focused caret cadence when idle, and stops for hidden editors. Rain reuses unchanged Flutter and Monaco textures without changing its shaders, density, resolution or animation cadence.

Page swaps and onboarding retain static layout and content between animation ticks; the startup logo is likewise retained. Their original transforms, curves, durations and reduced-motion behavior are unchanged. A 180-frame comparison across all five main themes and normal/compact layouts found identical pixels, with about 88% fewer main page-swap rebuilds and 91% fewer onboarding rebuilds in the measured test loops. Native rounded input masks reuse unchanged allocations and coalesce identical middle scanlines, with 4,913 geometry cases matching the original algorithm exactly. Scoped native frame styling prevents GTK theme borders or background images leaking through the transparent curved window edge.

Invisible main pages retain their last layout and inherited presentation during window morphs; visible and outgoing pages stay current, including custom themes. In a private Linux run of twelve unchanged 480 ms size morphs, p90 Flutter build time fell from 21.1 ms to 7.1 ms and sampled native size transitions increased from 123 to 213. This is a workload measurement, not an overall FPS guarantee. The final morph and navigation comparison preserved every pixel across 180 sampled frames. Native resize notifications now report actual top-level size/scale changes instead of internal child-layout churn. The script explorer caches its tree until the library, filter, or expansion changes; typing no longer rescans large script folders. Monaco isolates mirror pixel alignment from its widget tree, avoiding duplicate resize measurements. Glass reuses unchanged blur levels and allocates only the targets its active blur mode reads, retaining the same resolution, passes, kernels, and optics.

Isolated Linux WebKit measurements on this development machine reduced 60 completion/hover pairs on a 6,000-local script from 505 ms to 14 ms. Full-resolution snapshot encoding fell from 18–29 ms to about 7 ms; unchanged snapshots reuse the cached PNG. These are specific workload measurements, not overall frame-rate claims. Before/after pixel comparisons cover editor/autocomplete, theme controls and rain output.
